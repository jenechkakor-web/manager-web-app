# Интеграция Битрикс24

Обработчик сайта: `POST https://manager.verkup.ru/api/bitrix/events`.
Поддерживает JSON и стандартный `application/x-www-form-urlencoded` Б24.
Проверяет токен исходящего вебхука и домен портала до доступа к базе. Полную карточку читает через закрытый входящий вебхук; адреса и данные сделки из тела события не используются как доверенные данные.

## Подключение

1. Администратор приложения заполняет **ФИО** в разделе **Пользователи**. Укажите имя и фамилию как в Б24. Совпадение должно быть единственным. Допускаются только восемь сотрудников из `api/bitrix-rules.json`. Новые аккаунты интеграция не создаёт.
2. Б24 → Приложения → Разработчикам → Готовые сценарии → Другое → Входящий вебхук. Нужны области CRM и Пользователи, а у владельца вебхука — доступ на чтение всех нужных сделок и сотрудников. Используются `crm.deal.get`, `crm.status.list`, `user.get`.
3. Создайте исходящий вебхук на адрес обработчика для **ONCRMDEALADD** и **ONCRMDEALUPDATE**. Скопируйте его токен приложения.
4. В приложении откройте **Пользователи → Битрикс24 → Настройки подключения**, введите ключи и коды полей. Только администратор может сохранять настройки; ключи отправляются на собственный сервер по HTTPS и никогда не возвращаются в ответах API. Сервер атомарно сохраняет их в закрытом `api/bitrix.local.php`. Альтернатива — создать этот файл по образцу `api/bitrix.local.example.php`. Секреты не попадают в Git или резервные артефакты деплоя.
5. Поле «Предоплата» портала verkup.bitrix24.ru — `UF_CRM_1547663414463`; укажите его в `paidAmountField`. По подтверждённому правилу пользователя пустое значение (в том числе null/false Б24) означает полную оплату. Предоплата, равная «Сумма и валюта» (`OPPORTUNITY`), также означает полную оплату; меньшая сумма — частичную. При отсутствии настройки оплата отображается как «Планируется». Если заданный код вообще отсутствует в ответе API, синхронизация завершается ошибкой без изменения реестра.
6. Администратор может проверить `GET /api/bitrix/status` и повторить обработку конкретной сделки через `POST /api/bitrix/sync` с JSON `{"dealId":"123"}`. Эти методы требуют обычной сессии администратора; повторная обработка безопасна. После заполнения ФИО повторите обработку сделок, ранее пропущенных из-за отсутствия совпадения.

## Правила

- Владелец определяется по **CREATED_BY_ID** — создателю, независимо от текущего ответственного. Ошибочная или неоднозначная привязка пропускает сделку. Уже импортированная сделка не передаётся другому аккаунту при изменении настроек.
- Номер по умолчанию — ID сделки; дата — дата создания, название — TITLE, сумма — OPPORTUNITY, источник — название из справочника SOURCE. Реестр работает в рублях: другие валюты отклоняются. Денежные поля поддерживают формат Б24 `1000.00|RUB`.
- Правила трёх плановых, одиннадцати рабочих и финальной стадии перечислены в `api/bitrix-rules.json`. Учитываются пробелы, регистр и е/ё; стадии читаются из фактической воронки сделки. Неуказанные стадии сохраняются с «Планируется», пометкой `unmappedStage` и без бонуса. Их точное название видно в подсказке статуса.
- На плановых стадиях статус сделки и оплаты — «Планируется». На рабочих — «В работе», оплата — по правилу предоплаты выше. Полная сумма сделки, внесённая оплата и остаток хранятся раздельно.
- Только «Сделка завершена. Документы подписаны.» даёт статус «Завершена» и бонус по действующему типу расчёта сделки (по умолчанию 12%). Оплата и отправка документов не выдумываются по стадии. Для обычных сделок прежнее условие начисления не меняется.
- Повторные уведомления не создают сделку или начисление второй раз и сохраняют дату начисления. Бонус рассчитывается из текущей суммы сделки. Возврат из завершения убирает начисление; повторное завершение устанавливает новую дату — так же, как действующий реестр выплат.
- Б24 управляет названием, источником, датой, суммой, оплатой и стадией импортированной сделки. Ручное сохранение договора сохраняет эти значения. Тип бонуса, документы, реквизиты и шаблон договора остаются доступны в приложении.
- Отдельная таблица `manager_bitrix_deals` связывает портал и ID с записью. Существующая запись с совпавшим номером не перезаписывается: возвращается 409. Если задан `numberField`, номер реестра фиксируется при первом импорте; текущее значение хранится в `registryMeta.bitrix.number`. Удалённая запись не восстанавливается автоматически.
- Запись сделки, связи и даты бонуса выполняется одной транзакцией. Обработка одной сделки сериализована до чтения актуальной карточки; устаревший снимок не откатывает данные. Ошибки API оставляют прежние данные; повторную доставку Б24 нельзя считать гарантированной — используйте повторную синхронизацию после сбоя. Массовый исторический импорт и удаление сделок из Б24 не запускаются.

## Локальная версия и проверки

Для Node.js настройки из интерфейса сохраняются в `.data/bitrix.local.json`. Можно использовать другой закрытый JSON и передать абсолютный путь в `BITRIX_CONFIG_FILE`. Не используйте реальные сделки для тестов.

`node --test tests/payouts.test.cjs tests/bitrix.test.cjs` — локальные API и интеграция с имитацией Б24.

`php tests/bitrix-php.php` — правила и начисления PHP. В CI дополнительно проверяются PHP 5.6/8.1 и транзакции на отдельной MySQL-базе.

Документация Б24: [вебхуки](https://apidocs.bitrix24.ru/local-integrations/local-webhooks.html), [событие создания](https://apidocs.bitrix24.ru/api-reference/crm/deals/events/on-crm-deal-add.html), [поля сделки](https://apidocs.bitrix24.com/api-reference/crm/deals/crm-deal-get.html).
