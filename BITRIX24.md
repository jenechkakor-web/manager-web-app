# Интеграция Битрикс24

Обработчик сайта: `POST https://manager.verkup.ru/api/bitrix/events`. Поддерживает JSON и стандартный `application/x-www-form-urlencoded` Б24. Проверяет токен исходящего вебхука и домен портала до доступа к базе. Полную карточку читает через закрытый входящий вебхук; адреса и значения из тела события не используются как доверенные данные.

## Подключение

1. Администратор заполняет ФИО в разделе «Пользователи» точно как в Б24. Совпадение должно быть единственным. Разрешённые имена перечислены в `api/bitrix-rules.json`: Антон Исаков, Иван Дмитриев, Айк Ахвердян, Алексей Федоренко, Сергей Кирсанов, Кирилл Орлов, Николай Шляхтенко, Александр Стаценко, Алексей Купоров. Интеграция связывает существующие аккаунты и не создаёт новые.
2. Входящий вебхук Б24 должен иметь права CRM и Пользователи; его владелец — доступ на чтение нужных сделок и сотрудников. Используются `crm.deal.get`, `crm.deal.list`, `crm.status.list`, `user.get`.
3. Исходящий вебхук отправляет события `ONCRMDEALADD` и `ONCRMDEALUPDATE` на адрес обработчика.
4. «Пользователи → Битрикс24 → Настройки подключения» сохраняет ключи в закрытом `api/bitrix.local.php`. Только администратор может изменять настройки. API не возвращает ключи; Git и резервные артефакты деплоя их не содержат. Альтернатива — закрытый файл по образцу `api/bitrix.local.example.php`.
5. Коды полей предоплаты и полной оплаты больше не используются. Старые настройки можно оставить: они не влияют на реестр. Номер по умолчанию соответствует ID; при необходимости используется `numberField`.
6. `GET /api/bitrix/status` показывает состояние, `POST /api/bitrix/sync` с `{"dealId":"123"}` повторяет обработку одной сделки. Оба метода требуют сессии администратора.

## Передаваемые данные

Из Б24 обновляются только номер, название (`TITLE`), источник (название из справочника `SOURCE`) и полная сумма (`OPPORTUNITY`). Реестр поддерживает RUB/RUR. Другие валюты отклоняются.

Владелец определяется по `CREATED_BY_ID` — создателю, независимо от ответственного. Неоднозначное или отсутствующее совпадение с разрешённым пользователем пропускает сделку. Уже связанная запись не передаётся другому аккаунту автоматически.

Новая запись получает текущую дату приложения по Москве, оплату «Планируется», нулевую предоплату и внутренний статус «Планируется». Существующие дата, контрагент, предоплата, оплата, закрывающие документы, вид оплаты, тип бонуса и реквизиты сохраняются. Стадии и оплата Б24 не управляют реестром, дашбордом или начислениями, включая записи со старыми метаданными CRM.

Если новая сумма Б24 меньше уже внесённой предоплаты либо противоречит вручную отмеченной полной оплате, запись не изменяется; возвращается ошибка 409 с просьбой проверить сумму и предоплату. Финансовые условия реестра не корректируются автоматически ради импорта.

Номер фиксируется при первом импорте и не редактируется. Пользователь может редактировать остальные исходные значения своей записи с обычными ограничениями реестра. Менеджера и статус документа меняет только администратор. Остаток, статус сделки и процентный бонус рассчитываются автоматически; сумма бонуса «От прибыли» задаётся вручную. Повторное обновление из Б24 снова актуализирует название, источник и сумму.

## Внутренние статусы и вид оплаты

- Оплата «Планируется» означает статус сделки «Планируется».
- При «Предоплата» или «Да» сделка находится в работе.
- Полная оплата, нулевой остаток и закрывающие документы «Отправлены» или «Не нужно» дают статус «Завершена».
- Условие начисления бонуса сохранено: полная оплата с нулевым остатком и документы «Отправлены». Тип расчёта берётся из реестра. Повторное сохранение сохраняет дату начисления; выход из условий убирает квалификацию, повторное выполнение устанавливает новую дату. Ранее отменённые начисления не восстанавливаются.
- При выгрузке счёта в приложении `data.sellerKey=ip` устанавливает «ИП», `ooo` — «ООО». Для ранее выгруженных счетов пустой вид оплаты определяется по сохранённому выставителю. Выбранная вручную «Наличка» сохраняется при повторной выгрузке. Выставитель счёта из Б24 не читается.

## Кнопка пяти последних сделок

«Реестр сделок → Обновить данные с Б24» выбирает пять самых новых сделок Б24, созданных вошедшим пользователем, в порядке `DATE_CREATE DESC, ID DESC`. Включаются сделки, которых ещё нет в реестре. Фильтр менеджера у администратора меняет только просмотр таблицы и свода; обновление всегда относится к учётной записи, нажавшей кнопку.

`POST /api/bitrix/recent` с `{"action":"prepare"}` определяет создателя по ФИО и возвращает `runId` и до пяти `dealIds`. Список хранится в серверной сессии 30 минут. Далее клиент отправляет по одному `{runId, dealId}`. Сервер проверяет сессию, список, срок действия, текущего создателя Б24 и владельца существующей записи. Передать чужого менеджера или шестую сделку через параметры запроса нельзя. Отдельная ошибка не останавливает остальные сделки; результат отображается над таблицей.

Обычная числовая запись текущего менеджера может быть связана с тем же ID Б24 с сохранением исходной версии для аудита. Суффиксы и записи без номера не угадываются. Удалённые сделки не восстанавливаются автоматически.

## Автоматические события и массовое обновление

События создания и изменения продолжают обрабатываться по мере доставки Б24, теперь только для указанных четырёх полей. Периодического таймера нет; после пропуска доставки можно нажать кнопку последних пяти или повторить обработку конкретной сделки. Повторные уведомления не дублируют записи. Обработка одной сделки сериализована до чтения карточки; устаревшие данные не откатывают новые. Ошибки API сохраняют прежнее состояние.

Отдельная таблица `manager_bitrix_deals` связывает портал и ID с записью. Обычный вебхук не перезаписывает несвязанную запись с совпавшим номером: возвращает 409. Для её связывания предназначены явные режимы обновления. Изменение создателя или ручная смена владельца требует разрешения конфликта, а не скрытой передачи записи.

Кнопка администратора «Пользователи → Битрикс24 → Обновить все сделки из Б24» остаётся отдельным режимом. Она обрабатывает текущие записи по одной и не добавляет новые. `GET /api/bitrix/refresh` возвращает список номеров, `POST` принимает `number` и UUID `runId`. Только администратор имеет доступ. Создатель должен совпасть с текущим владельцем, особые номера пропускаются.

Перед явным обновлением существующей записи PHP атомарно сохраняет исходную строку и дату бонуса в `manager_bitrix_refresh_history`. Повтор запроса с тем же `runId` возвращает прежний результат после проверки владельца. Локальная версия использует `.data/bitrix-refresh-history.json`. Запись, связь и дата квалификации сохраняются одной транзакцией.

## Проверки

Node.js хранит настройки в `.data/bitrix.local.json`; альтернативный закрытый путь задаётся `BITRIX_CONFIG_FILE`. Тесты используют только изолированные данные и имитацию Б24.

- `node --test tests/payouts.test.cjs tests/bitrix.test.cjs tests/proposal.test.cjs` — права, четыре поля, редактирование, пять последних, защита владельца, оплата и бонусы.
- `php tests/bitrix-php.php` — правила PHP; CI дополнительно проверяет PHP 5.6/8.1 и транзакции на отдельной MySQL 5.7.
- `node tests/payouts-php-http.cjs` при `PAYOUT_TEST_MYSQL=1` — HTTP API PHP на тестовой базе, включая редактирование и выставителя счёта.
- `node tests/registry-ui.cjs <путь к playwright> <путь к браузеру>` — изолированная проверка интерфейса, кнопок менеджеров, свода, редактирования и обновления пяти своих сделок при просмотре чужого менеджера.

Документация Б24: [вебхуки](https://apidocs.bitrix24.ru/local-integrations/local-webhooks.html), [событие создания](https://apidocs.bitrix24.ru/api-reference/crm/deals/events/on-crm-deal-add.html), [список сделок](https://apidocs.bitrix24.ru/api-reference/crm/deals/crm-deal-list.html).
